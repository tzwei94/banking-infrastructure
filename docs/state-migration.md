# Moving existing state to the single dev root

Use this procedure when moving an existing foundation/platform/release deployment into the single dev root. For a fresh environment, follow the README bootstrap instructions instead.

The [address map](state-address-map.json) maps all previous foundation/platform/release resource declarations to the new module addresses. Preserve each existing instance suffix (`[0]`, `[1]`, `["app"]`, and so on). Backend bootstrap resource addresses are unchanged; only its source directory moved.

1. Pause deployment dispatch and coordinate an exclusive maintenance window. Verify the account/region and the actual old state keys. Download versioned, encrypted backups of each old state to an access-restricted operator workspace. State files can contain private data; do not commit them or put them in chat.
2. Configure the independent backend/OIDC bootstrap roots and the complete dev input profile. Copy current names, region, CIDRs, final-snapshot identifier, images, source SHA, service-enabled state and active ARN exactly. A directory rename is not permission to rename existing AWS resources. In particular, existing `banking-demo` resources should keep that name during migration, even though the new default/example is `banking-dev`.
3. Move the OIDC provider's ownership from the old foundation state to the independent OIDC bootstrap state, preserving the same provider ARN. For every other mapped resource, merge ownership into a staging dev state and change the address to the listed module prefix. Use reviewed `terraform state mv -state=... -state-out=...` operations on protected local copies, or an explicit import-and-remove procedure with recorded IDs. Do not import into dev while leaving another active root managing the same resource.
4. Review the merged state inventory against all source inventories. Every original instance must have exactly one destination owner. Preserve the successful release manifest key/name and its retained task-definition ARNs. Keep the existing backend state separate.
5. Install the reviewed destination states into their intended backends with appropriate locking/version checks. The dev key is `dev/terraform.tfstate`; OIDC may use `bootstrap/github-oidc/terraform.tfstate`. Do not use blind `state push -force` or treat `init -migrate-state` on a single old root as a merge of all three states.
6. Run full operator refresh/plan with matching live inputs. Resolve all unexpected create, destroy or replace actions before any apply. Review the intended new deployment IAM read permissions/state-key changes separately. Confirm rollback references and the service's active task ARN remain correct.
7. Retire the old configuration/state ownership only after backup integrity, destination plans and ownership are verified. Keep historical state versions and the address inventory according to the operator's retention policy. Update protected GitHub environment variables and OIDC settings, then re-enable release dispatch.

The release script deliberately rejects infrastructure changes in its saved plan. It cannot perform this migration or repair infrastructure drift. Release automation can read the entire dev state; restrict access to trusted operators.
